Tensor 类层次开发过程笔记

目标：从零搭一套可对接 llama.cpp / ggml 的张量类层次，支持 0~4 阶张量、运行时多态、零拷贝视图（转置 / 任意轴 permute），并保留“裸指针 + 内存池友好”的存储设计。

. 总览

. 设计目标与初始约束

  1. 类层次：基类 Tensor，派生 Scalar(0阶) / Vector(1阶) / Matrix(2阶) / Tensor3(3阶) / Tensor4(4阶)。

  2. 不用 std::vector 存数据：直接用 new 分配 data_，为后续接入内存池留口子（基类 allocBuffer / freeBuffer 两个静态函数即内存池接入点）。

  3. ggml 类型标签：引入 ggml.h 的 enum ggml_type 作为“张量存储数据类型”的格式标签；计算缓冲 data_ 始终是 compute_type（当前 = float / F32）。即 type_ 是“声明/序列化类型”，与真实存放的浮点缓冲解耦。

  4. 运行时多态：统一用 Tensor* / unique_ptr<Tensor> 管理各类张量，基类提供统一访问入口。

. 整体架构（v15 当前状态）

基类 Tensor

  • 成员：compute_type* data_（裸指针）、ggml_type type_（类型标签）、shape_type shape_（各维尺寸）、shape_type stride_（各维元素步长）、size_t count_（元素总数）、bool owns_data_（视图置 false，析构不释放共享缓冲）。

  • Rule of Five：Tensor 自己管理裸指针——析构按 owns_data_ 决定是否 freeBuffer；提供深拷贝（copy 得到独立缓冲）与移动（搬运指针，零拷贝）。

  • 统一访问虚入口：virtual compute_type& operator()(size_t a=0,b=0,c=0,d=0) 的 4 参数版本（const / 非 const 两版）。基类全带默认值 =0，派生类“本阶实际用到的下标”为真实索引（不带默认），超出本阶的下标默认 =0 并忽略——这样经 Tensor* 多态调用时用户不必填多余下标。

  • offset(idx) 为 virtual，按 stride_ 计算 Σ idx[k]*stride_[k]；普通稠密张量由 allocate() 设定标准行主序步长，视图类重写 offset() 实现零拷贝重排。

  • 通用接口：get({idx...}) / set({idx...})、view()（identity 排列全视图）、permute(perm)、clone()（物化独立张量）、describe()、type()、strides()。

派生张量

  • Scalar / Vector / Matrix / Tensor3 / Tensor4：各自 rank()、dims()、typeName()、对应阶数的 operator()、以及具体类型的便捷 get/set/at。

  • Matrix 额外提供 transpose() 返回 unique_ptr<TransposeView>。

  • Tensor3 / Tensor4 额外提供 swapaxes(a,b)（数字轴 + 命名轴两版）。

视图（零拷贝别名）

  • TransposeView : public Tensor（独立类，v14 恢复）：构造共享 Matrix::data_，owns_data_=false，shape_={cols,rows}，重写 offset() 为 j*srcCols+i，自带 clone()（物化为 Matrix）、source()、describe()。

  • PermuteView : public Tensor：构造时 shape_[k]=src.dims()[perm[k]]、stride_[k]=src.strides()[perm[k]]、data_=src->data()、owns_data_=false；重写 offset/operator()/clone/describe。是“任意轴重排”的通用实现，与 ggml 的 nb[] 字节步长同构（只是单位为“元素”）。

  • 视图语义铁律：不拥有内存，源张量必须比视图活得久；clone() 把视图数据拷进独立缓冲，脱离源仍可存活。

命名轴枚举 Axis

enum Axis : size_t { axisX = 0, axisY = 1, axisZ = 2, axisW = 3 };

  • 底层 size_t，可隐式转 size_t 喂 vector<size_t>，用来代替裸数字下标，使转置 / 轴重排更直观。

  • 基类提供 permute(initializer_list<Axis>) 重载；Tensor3/Tensor4 提供 swapaxes(Axis,Axis) 重载。

  • 例：矩阵转置 = m.permute({axisY, axisX})；三阶轴轮转 = t3.permute({axisZ, axisX, axisY})；四阶轴交换 = t4.swapaxes(axisY, axisW)。

v10 与 ggml_tensor 兼容性分析

  • 对比 ggml.h 的 ggml_tensor：概念相似（都是描述张量形状/步长/类型的结构体），但存储语义不兼容——

    • ggml 的 data 按 type 真存量化块（如 Q8_0 每 32 个元素一组），nb[] 是字节步长；

    • 本 wb::Tensor 的 data_ 恒为 float*，stride_ 是元素步长，type_ 仅作标签。

  • 结论：当前 type_ 是“声明类型”，要做到“真正按该类型存字节”需把 data_ 改成 void* + nb[]（留作后续可选项）。

  • 版本一：TransposeView : public Matrix（复用 Matrix 接口）。

  • 此版一度把 TransposeView 改为 PermuteView 的特化子类。

  • 基类加 permute(initializer_list<Axis>) 重载；Tensor3/Tensor4 加 swapaxes(a,b) 命名轴版（swapaxes(Axis,Axis)）。

  • main.cpp 的 8.9 / 8.10 演示改用命名轴，可读性显著提升。

关键技术要点

  1. Rule of Five + owns_data_ 标志：视图与所有者共用同一套析构逻辑，靠 owns_data_ 防止误释放共享缓冲。

  2. stride[] 偏移模型：offset(idx)=Σ idx[k]·stride_[k]，与 ggml 的 nb[]（字节步长）同构，只是单位从字节变元素。permute 只重排 stride_ / shape_，零数据拷贝。

  3. 视图 vs 物化：视图共享存储、零拷贝、clone() 才物化为独立张量；源须比视图活得久（典型 view 语义）。

  4. 统一 operator() 虚分发：基类 4 参数全默认，派生类按阶数去掉对应默认参数，经 Tensor* 多态调用时签名一致、正确分发。

  5. 命名轴枚举：Axis 底层 size_t，可读性地替代裸数字下标，降低转置/重排的理解成本。

  6. 内存池接入点：allocBuffer / freeBuffer 两个静态函数集中封装分配/释放，将来换内存池只改这两处。

v2.0 存储模型重构（Tensor20.h，与 ggml 同构）

把 1.x 的 float* data_ + 元素步长 stride_ 改造为与 ggml_tensor 同构的 void* data_ + 字节步长 nb[]，并加 type 感知访问。

核心改动

type 感知访问（readElem / writeElem）

按 type_ 把 (char*)data_ + 字节偏移 处的字节解释/写入：

  • F32：恒等快路径；operator()& / at() 返回真实 float&。

  • F64 / I8 / I16 / I32 / I64：按对应整数/双精度类型存取，经 compute_type(float) 转换（标量类型精确往返整数；F64 经 float 接口读出有 float 精度）。

  • F16 / BF16：用 float_to_fp16 / bf16_to_float 等最小实现互转（覆盖常规范围，生产可替换为 ggml 的 ggml_fp16_to_fp32）。

  • 量化类型（Q4_0/Q8_0/Q_K…）：elemBytes 抛“无逐元素字节数”，readElem/writeElem 抛“需专用 dequant/quant，暂未实现”。operator()& 仅在 type_==F32 有效，非 F32 抛清晰错误并引导用 get()/set()。

视图（零拷贝）随之同构

  • PermuteView / TransposeView 的 nb_ 直接取自源的 nb[]（字节）按轴重排，offset() 基类即可算出正确字节偏移——因此移除了两者原先重写的 offset()，更贴合 ggml 思路（只改 nb[] 映射，不搬数据）。

  • data() / raw() 改为返回 void*（与 ggml 同）；新增 nb() 别名（ggml 风格），strides() 保留为兼容别名。

  • strides() / nb() 现在返回的是字节步长，注意与 1.x 的“元素步长”语义不同（行主序下 nb[轴0] > nb[轴1]，如 2×2 F32 = [8,4]）。

PermuteView 在三阶 / 四阶中的统一机制（图解）

本节用三张图回答一个核心疑问（对应 v15 第 17 条讨论）：PermuteView 在三阶张量与四阶张量里，机制是否不同？

结论先行：完全相同——都是「只重排 shape_ 与 nb_（v2.0 的字节步长，旧称 stride_），数据块原封不动共享」。区别仅在于阶数越高、可交换的轴越多。下面三张图从「机制总览 / 三阶实例 / 四阶实例」三个角度讲清同一件事。

小结（三张图共同说明的一件事）：PermuteView 的本质是「换一副眼镜看同一块内存」——它把源张量的 shape_ 与 nb_（步长）按 perm 重新排列，得到一套新的「形状 / 步长」映射；而底层的 data_ 字节缓冲从头到尾一个比特都没动，视图与源共享同一地址。无论是三阶还是四阶，这套机制完全相同，差异只是阶数越高、可排列的轴越多（排列组合数 3!→4!）。这也正是 main.cpp 里 rot(i,j,k)==t3b(j,k,i)、sa4(i,j,k,l)==t4c(i,l,k,j) 能恒成立的原因——它们读的是同一块内存，只是用不同的轴顺序去索引。

ElemRef 引用代理：标量非 F32 类型全功能化（operator()/at）

对应讨论：能否让 operator()&/at() 对 F16/BF16/I8/I16/I32/I64/F64 等「标量非 F32 类型」也像 F32 一样读写？

为什么不能直接返回 float&

operator() 的原返回类型是 compute_type&（即 float&）。F32 时缓冲区里本就是 float，可 reinterpret_cast<float*> 拿到真实引用；但 F16 缓冲区里是 uint16 半精度、I8 是 int8——这些字节里根本不存在 float 对象，物理上无法返回一个指向它们的 float&。旧实现因此对非 F32 直接抛异常、引导改用 get/set。

解决方案：引用代理（reference proxy）

仿照 Eigen / std::vector<bool> 的成熟模式，新增 class ElemRef，operator()/at 改为返回该代理（而非 float&）：

  • F32：代理内部持有真实 float*，读/写/取地址零开销，行为与旧 operator()& 一致；

  • 其他标量类型：构造时「读出 float 缓存」，赋值时「经 Tensor::set 写回（float → 真实存储类型）」；

  • 额外提供 += / -= / *= /= 便捷算术，使 m(i,j) += x 可用；

  • 来自 const 张量时只读，写入抛清晰错误。

基类纯虚 operator()（含 const 版）返回类型由 compute_type& 改为 ElemRef；各子类（Scalar/Vector/Matrix/Tensor3/Tensor4/PermuteView/TransposeView）的 operator() 与 Tensor3/Tensor4 的 at() 同步改为返回 ElemRef，内部统一经 refElem(idx)（原 refAt）构造代理。ElemRef 需 friend 访问受保护的 offset()。

效果

  • F32：零开销，行为与之前完全一致；

  • F16/I8/I16/I32/I64/F64：全功能，支持 m(i,j) = x、float x = m(i,j)、m(i,j) += x 等写法；

  • 注意：operator() 现在返回代理而非 float&，故 float& r = m(i,j);、&m(i,j) 这类「取真实 float 引用 / 取地址」不再编译（&m(i,j) 取的是代理临时量地址，无意义）；需要真实引用时仍仅限于 F32 且应改用 raw()/data() 直接操作。

  • 量化类型（Q4_0/Q8_0/Q_K…）仍未实现（get/set 抛「未实现」），且 elemBytes 的量化判定 bug 仍在（见下）。

验证

  • Qt MinGW g++ -std=c++17 -Wall -Wextra 零错误零告警；main.cpp 全量自测通过。

  • 额外临时用例（已清理）验证：F16/I8/I32 经 operator() 代理读写往返正确、F16 代理 +=/*= 正确、F32 直连读写正确、Matrix 非 F32 operator() 写入正确——全部 PASS。

模型文件里到底存了什么 "token 信息"

GGUF 文件里和 "token" 相关的其实有两块，都和 KV 缓存无关：

  1. 权重侧的嵌入/参数矩阵（embedding、各层线性层）：这才是能用 q8_1 量化来省文件 + 显存的东西——这部分理解完全正确。

  2. 分词器词表（tokenizer）：就是一张 token 字符串 ⇄ ID 编号 的对照表（外加 BPE 合并规则、token 分数等）。这张表是固定的、离散的映射，跟数值精度毫无关系——不论用 float32 还是 q8_0，词表里第 12345 号 token 还是那个 token，编号一个都不会少、也不会变。

--cache-type-k / -v 改的是"运行时的 KV 缓存"，不是文件

KV 缓存（Key/Value 矩阵）根本不在模型文件里。它是模型加载后、推理时才产生的：

  • 注意力机制里，每个 token 经过某一层、某个头，会算出一对 K 向量和 V 向量。

  • 推理时分两步：先把提示词"预填充"（prefill），算出所有 token 的 K/V 存起来；之后每生成一个新 token，就把它的 K/V 追加进缓存，供后续注意力查表。

  • 所以 KV 缓存大小 ≈ 层数 × 头数 × 已生成 token 数 × 每个 K/V 的维度 × 精度。上下文越长，它越大，经常是显存大头。

  • --cache-type-k q8_0 的意思：把这个运行期才产生的 K/V 缓冲，用 q8_0（8-bit）来存，而不是默认 float16。目的就是砍显存占用。它一个字节都不碰 GGUF 文件。

为什么"用了 q8_0 就不能对所有头/token 编号"是误解

担心的"不能对所有头编码进行编号"，两种解读都说明：

  • 若"头肯"= token：token 编号来自分词器词表（第 11.2 节），KV 缓存量化碰不到它。无论 KV 缓存用什么精度，词表、token ID、编码方式原封不动。

  • 若"头肯"= 注意力头（attention head）：量化是逐头（per-head）做的——每个头的 K、V 向量各自用 8-bit 压缩存储，头的个数、序号、连接关系完全不变，只是每个头里的数值精度从 16-bit 降到 8-bit。所以"所有头都能正常编号、照常参与注意力"，只是存得更省。

  • 一句话：q8_0 改的是"每个向量怎么存（8-bit + 一个 scale）"，不改"有哪些向量、怎么编号"。

这正好暴露了 Tensor20.h 里 type_ 的 "标签 vs 真存储" 区别

这里用上了之前 v10 的结论：

  • wb::Tensor 里 type_ 只是个标签，data_ 永远是 float*；

  • 而 ggml 里 type 是真存储类型——GGML_TYPE_Q8_0 意味着这块缓冲真的被按 8-bit 块打包（每 32 个数 + 1 个 fp16 scale）。

  • KV 缓存之所以能被 q8_0 压缩，正因为 ggml 的 data 是 void*、按 type 真解释；而你的类现在"标 q8_0 实际还是 float"，所以 Tensor20.h 目前还做不到真正的 KV 缓存量化——得先把 data_ 改成 void* + nb[] 字节步长、加解包逻辑（即"真·ggml 兼容版"，见第 8 节）。

实际怎么选

  • --cache-type-k q8_0 --cache-type-v q8_0：显存省一半多，质量几乎无损（K/V 对精度不敏感），长上下文首选。

  • 想更保守：可以 q8_0 只压 K、V 保持 f16，或反过来。

  • 模型权重本身的量化（q8_1 / q4_K 等）是另一回事，在转换/下载模型时就定了，跟运行期 KV 缓存是两笔账。

备注：本笔记第 8 节已将 data_ 改造为 void* + nb[] 字节步长（真·ggml 同构），但量化类型（Q8_0）的 pack/unpack + dequant 尚未实现——即 11.5 所说的"解包逻辑"仍待补，对应第 7/8 节的可延伸方向。

量化张量的"存储 vs 计算"数据流（Q8_0 省内存的本质）

背景：在决定把 Tensor20.h 的计算函数分成「成员原语」与「推理计算层自由函数」之前，先厘清量化张量在内存与计算之间的真实数据流。本节纠正了「Q8_0 张量全程在内存里是 Q8_0、计算时 unpack 成 F32 算、结果再 pack 回 Q8_0」这一直觉模型。

直觉模型里对的部分（核心正确）

  • Q8_0 张量的数据在内存/显存里确实是 Q8_0 格式（int8 块 + fp16 scale），不是 float。 这正是量化的全部意义——权重体积砍到约 1/4，省的是真金白银的显存。

  • 参与计算时必须先「解量化」成 F32（或 F16）才能做乘加。这点也对。

需要修正的两点

修正①：反量化不是「整张 unpack 成 F32 → 算 → pack 回」的往返。 真实 ggml 的 MUL_MAT（矩阵乘，占推理 99% 算力）用的是融合内核（fused kernel）：

xxxxxxxxxx
内核里逐元素、在寄存器层面现场反量化：
    w_ik = q_ik * scale_i          // 不是先解量化整张权重
    acc  += w_ik * x_jk            // x 是 F16/F32 激活，累加到 F32 累加器

它从不物化一整份 F32 权重矩阵。原因很硬：若先把 Q8_0 权重整体解量化成 F32，内存瞬间 4 倍（省的那点又吃回去了），还白费一遍解量化带宽。所以「pack/unpack 函数」在热路径上其实是内核里的内联操作，不是独立的整张张量往返。

修正②：计算结果一般并不 pack 回 Q8_0。

  • matmul / 注意力 / 激活 / logits 的结果是 F16 或 F32，不会被重新量化回 Q8_0。

  • 只有显式配置要量化的东西才会 round-trip，最典型的就是第 11 节研究的 KV 缓存（--cache-type-k v q8_0：算出 K/V → 量化存 → 注意力要用时再解量化）。

故「计算结果仍以 Q8_0 存」——对 KV 缓存成立，对一般激活不成立。

正确的两条数据流

xxxxxxxxxx
【权重路径】（直觉里"对"的那部分）
  磁盘 GGUF ──加载──▶ 内存/显存里就是 Q8_0（int8+scale），永久保持
                              │
  计算：融合内核内联解量化（不物化 F32 副本）──▶ 结果 F16/F32（不回量化）


【KV 缓存路径】（直觉"完全对"的那部分，也是唯一 round-trip 的）
  算出 K/V (F32/F16) ──quantize──▶ 存成 Q8_0（省显存）
         │                                     │
         └──── 注意力要用时 dequantize ─────────┘（解量化回 F32 参与计算）

术语纠正

  • 这里说的 「pack/unpack」 在 ggml 里对应：

    • dequantize：Q8_0 → F32（即 unpack）

    • quantize：F32 → Q8_0（即 pack）

  • ggml 另有 ggml_pack，那是为特定计算内核重排权重布局（CPU compute packing），不是量化，勿混。

对本项目 Tensor20.h 设计的影响（呼应第 11 节 / 第 8 节）

  1. quantize / dequantize 是「推理计算层」原语（带 Q 块类型派发，不是 Tensor 成员的强制行为）——正好归到上一轮「成员 vs 计算层」分层里的计算层自由函数。

  2. 学习版可以简化：可先做「dequantize() 整张 → F32 算 → quantize() 回 Q8_0」这种显式往返。思路正确、结果等价，只是峰值内存和性能不如融合内核——对学习/理解概念完全够用。

  3. 但要知道生产 ggml 是融合内核的，所以真正 mul_mat 不该「先解量化整张权重」，而应「内核里内联解量化」——这是 Tensor20.h 以后接真实量化 kernel 时要补的那一步（对应第 8 节「量化类型 pack/unpack 待补」）。

一句话收束：量化张量存储是 Q8_0（省内存）✓；计算时解量化成 F32 ✓；但解量化是内核内联逐元素、不是整张往返，且结果通常不回量化（KV 缓存是唯一例外）。「Q8_0 全程 Q8_0 存、结果 pack 回」的模型对 KV 缓存完全正确，对权重 matmul 是简化近似。

推理所需 Tensor 成员函数清单（设计规范）

背景：在确认「量化适配（第 8/12 节）」与「成员 vs 计算层分层（第 11 节边界讨论）」之后，进一步梳理——为完成一次大模型（Transformer）前向推理，Tensor 类需要补齐哪些「计算成员函数」。 结论前置：Tensor 只补「与架构无关」的通用数值原语；凡含「模型结构知识」（归一化维度 / 位置频率 / 因果掩码 / 头划分）的算子，留在推理计算层用自由函数组合（见 13.6）。 约定：签名风格与现有 Tensor20.h 一致——compute_type=float、ggml_type type_、ElemRef、index_type/shape_type，所有原语经基类 get/set（虚访问）迭代，使 TransposeView/PermuteView 自动复用。 本文档是设计规范，尚未改动 Tensor20.h。

分层回顾（一句话）

  • 进类的 = 你定的四类：向量 / 向量×矩阵 / 矩阵×矩阵 / 三·四阶 Tensor 间计算。

  • 留计算层的 = rmsNorm / rope / attention / swiglu / kvCacheUpdate（含模型结构知识，自由函数 ops:: 组合成员原语）。

C.1 matvec —— 向量×矩阵（最高频）

xxxxxxxxxx
Tensor matvec(const Tensor& x) const;   // y = W·x

  • 要求：this 视为 [M, N]（或视图等效），x 为 [N] 向量，返回 [M]。

  • F32 路径：逐行 y_i = Σ_j W_ij · x_j，可直接用 float* 行指针 + x 行指针累加。

  • 用途：QKV 投影、输出投影、FFN 的三个 matvec 全部走它。

  • 说明：纯推理中 GEMM 出现较少（多为 GEMV），但 FFN、部分层、以及 bmm 的退化都会用到。

D 类 · 三/四阶 + 量化桥

D.1 bmm —— 批矩阵乘（多头注意力核心）

xxxxxxxxxx
Tensor bmm(const Tensor& B) const;   // A:[B,M,K] × B:[B,K,N] → [B,M,N]

  • 功能：对批维度每个切片独立做 matmul。注意力里每个 head 独立算 Q·Kᵀ 与 scores·V 都靠它。

  • 实现：循环每批切片调 matvec/matmul；Q 权重同样走 vec_dot 融合。

D.2 gather —— 索引取片（Embedding 查表）

xxxxxxxxxx
Tensor gather(const Tensor& indices, int axis = 0) const;

  • 功能：沿 axis 按 indices 取值。weight[vocab, dim] + indices[seq] → [seq, dim]（或 [batch,seq,dim]）。

  • 实现：对 indices 每个值 i，拷贝 this 沿 axis 的第 i 个切片到输出。Embedding 步骤唯一需要的「查表」原语。

D.3 dequantize / D.4 quantizeTo —— 量化桥

xxxxxxxxxx
Tensor dequantize() const;              // Q → 新 F32 张量（整张解量化）
Tensor quantizeTo(ggml_type t) const;   // F32 → 目标 Q 类型（整块量化）

  • dequantize：逐块调 QuantTraits::dequant，返回 F32 副本。用于调试或少数需 F32 精度的路径；普通推理不必调（matvec 已融合，省内存）。

  • quantizeTo：逐块调 QuantTraits::quant。用于 KV cache 写入、权重加载后格式转换。t 须为已适配类型，否则 traitsOf 抛"未适配的 ggml_type"。

明确不进类（留在推理计算层 ops:: 自由函数）

这些含「模型结构知识」，用 13.2–13.5 成员原语组合：

三条贯穿设计约束

  1. in-place vs 新张量：逐元素/归约给「返回新」+「InPlace」两套；matvec/matmul/bmm/gather 一律返回新张量（推理中间结果不可变更安全）。

  2. 量化结果策略：除 quantizeTo/kvCacheUpdate 显式回量化外，所有运算结果都是 F32。

  3. 视图复用：所有原语经 get/set（基类虚访问）迭代，TransposeView/PermuteView 只需重排索引映射即可自动参与——无需为视图单独重写算法。

实现顺序（建议）

  • Tier 1（覆盖 80% 底层）：A 核心（exp/rsqrt/silu/add/mul/scale）+ B（sum/mean/max/softmax）+ C.matvec（含 Q 融合）。落地后即可验证 RoPE / Attention 的分数计算。

  • Tier 2：A 余下 + B 余下（argmax/norm/var）+ C.matmul + D.bmm/gather。

  • Tier 3：D.dequantize/quantizeTo。

一句话收束：第 8/12 节的量化适配 + QuantTraits 表，已经是 C 类 matvec 量化融合内核与 D 类量化桥的底座；补齐 13.2–13.5 的成员原语后，13.6 的模型语义算子全部可由自由函数组合，无需进类。
